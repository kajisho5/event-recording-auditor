# False-Positive Control

Spec section 10 lists the false-positive classes this project must
actively guard against. This document tracks, for each one, whether it's
mitigated, how, and what the residual risk is. "Mitigated" never means
"eliminated" -- every mitigation here reduces false-positive risk while
preserving the "insufficient evidence -> human review required" fallback
rather than forcing a classification.

| False positive to avoid | Mitigation | Residual risk |
|---|---|---|
| Flagging intentional slide returns | `slide_rollback_pattern` downgrades confidence to LOW and severity to LOW when the intervening slide was displayed for a substantial duration (not brief) -- see `SlideRollbackPatternDetector._build_event`. | A presenter who quickly (but intentionally) flips back to a previous slide for a few seconds still looks like a "brief" revisit and gets MEDIUM confidence. This is why the finding is always phrased as "possible" and marked for human review, never as a confirmed mistake. |
| Flagging normal long explanations | `progression_interruption` requires audio inactivity AND visual inactivity AND unchanged slide, sustained together, before flagging anything (spec section 5). A presenter talking normally has active audio, so this alone never triggers it. | None known for this specific case; the detector is designed exactly to not flag this. |
| Flagging music as feedback | The experimental feedback detector requires narrow-band spectral persistence at a *fixed* dominant frequency across consecutive windows (`freq_tolerance_hz`), which sustained musical passages with pitch movement/harmonic content tend not to hold as tightly as an actual feedback loop. It is off by default and always emits `confidence<=medium` with an explicit "cannot reliably distinguish from a sustained musical note" caveat. | A single sustained pure tone (e.g. a test tone, a held note on a synth) can still trigger this. This is exactly why it is experimental and opt-in, not part of any default profile. |
| Flagging normal camera shots as freezes | `FreezeDetector` checks concurrent audio activity via the level envelope; freeze + active audio -> `severity=low, confidence=low` with an explicit "likely a normal static camera shot" interpretation. | On a recording with **no audio track**, or where the camera shot coincides with actual silence (e.g. a silent video-only feed), this mitigation cannot apply and the freeze is judged on duration alone at `confidence=medium`. Also: `freezedetect` genuinely cannot tell a frozen camera from a genuinely static presentation slide -- see docs/detection-model.md, "Known false-positive class". |
| Flagging audience Q&A as progress interruption | Q&A involves audio activity (questions, answers, murmuring) and usually visual activity (people standing, turning, camera pan) -- both of which prevent `progression_interruption` from firing. | A Q&A segment with an inactive/muted room mic and a static wide shot could still be flagged. The event's interpretation text explicitly names "audience working on a task" as an alternative explanation the recording cannot rule out. |
| Flagging intentional black transitions | `BlackoutDetector` always phrases its interpretation as "possible blackout ... or an intentional black transition. The recording alone does not establish intent." Severity scales with duration (a quick fade-to-black is LOW, not HIGH). | No durationless way to tell "signal loss" from "intentional cut to black" exists from pixels alone; this is called out rather than solved. |
| Flagging normal fade transitions | Same mechanism as above -- `blackdetect`'s `pic_th`/`pix_th` thresholds (0.98 / 0.10 by default) require a large fraction of the frame to be genuinely near-black, so a fast cross-fade rarely holds long enough at that threshold to register as a full black segment; when it does, it is short and gets LOW severity. | A slow fade-to-black-and-back (common in polished intros) can register as a real, if short, black segment. |
| Flagging normal silence between speakers | `AudioDropoutDetector` only flags a silence run that is (a) within a bounded duration window (`min_dropout_duration` to `max_dropout_duration`, default 0.4-6.0s) and (b) has audio active immediately before **and** after, using a stricter "active" threshold than the "silent" threshold (hysteresis). Raw `silencedetect` results are never surfaced as findings on their own. | A very short natural pause that happens to fall inside the dropout duration window can still be flagged as MEDIUM/LOW confidence; the finding text acknowledges this ("cannot be distinguished from a very short deliberate pause with certainty"). |
| Flagging animated slides as multiple slide changes | The slide-state timeline (`slides/timeline.py`) matches a new segment against *all* previously-seen canonical hashes, not just the immediately preceding one, within `match_threshold`. A slide with a build animation (bullets appearing one at a time) will register as several segments if the visual delta between steps exceeds `stable_threshold`, but `brief_unexpected_slide` and `slide_rollback_pattern` both key off *duration* and *pattern*, not raw segment count, so a fast animation sequence with no reversion pattern does not, by itself, produce a rollback finding. | An animation step that happens to look enough like an earlier slide (within `match_threshold`) could be misassigned to that earlier state's ID, which could coincidentally shape into an `A -> B -> A` pattern. This is a real, currently unmitigated edge case; increasing `stable_threshold`/`match_threshold` trades this risk against missing real slide changes. |
| Flagging an intentional mono-on-one-channel mix as a channel fault | `ChannelImbalanceDetector` splits this into two severities: a channel that's fully *missing* (near-silent) while another is active gets MEDIUM/HIGH as a likely dropped mic/routing fault, but a sustained *imbalance* where both channels are still somewhat active only gets LOW severity/confidence, explicitly noting it "could be an intentional mix choice". | An intentionally hard-panned mono source (one channel silent by design, not just quieter) still looks identical to a dropped channel from levels alone, so it lands in the higher-severity `channel_missing` bucket regardless of intent -- this is why confidence is capped at MEDIUM, not HIGH. |
| Flagging non-presentation footage as slide anomalies | Found running against real (non-slide) video: ordinary footage changes on essentially every sampled frame, so the slide-state timeline never holds a state for long and `brief_unexpected_slide` fired on nearly every state (105 findings on a 57s clip in testing). Both `SlideRollbackPatternDetector` and `BriefUnexpectedSlideDetector` now check `AnalysisContext.slide_stability_ratio()` first and skip entirely (recorded as a limitation) when less than 35% of the analyzed duration is spent in states held >=2s -- a real slide deck scores ~0.9+, this failure case scored ~0.05. | The 35% threshold is a single calibration point from real clips plus synthetic fixtures, not a validated boundary; content with an unusual mix (e.g. a slide deck that's mostly full-motion embedded video) could still be misjudged either way. |
| Flagging edited (non-slide) video that cuts between a few repeated shots as slide rollback | Found running against a second real clip: a portrait short-form video cutting back and forth between two camera angles/shots produces the *same* A -> B -> A revisit signature as a real slide rollback, including a high stability ratio (each shot is held steadily) -- so the mitigation above did not catch it (25 findings on a 195s clip in testing). Added a second, independent gate: slide decks and screen shares are virtually always landscape, so both detectors also skip when `AnalysisContext.aspect_ratio()` is below 1.2 (excludes square and portrait video). | This only catches the failure mode when the video is square/portrait. A **landscape** interview/vlog/broadcast edit that cuts back and forth between a small number of repeated camera angles would produce the same signature and is not currently protected against -- neither gate applies to it. No real landscape example of this has been tested yet; it's a known, undemonstrated gap. |
| Flagging normal source switching | Not currently applicable: source-switching detection (camera vs. slide identification) is explicitly not implemented yet (see docs/detection-model.md, "Deliberately not yet implemented") specifically because it cannot be done reliably without additional input, which would make false positives on this category likely. Nothing ships that could produce this false positive today. | N/A until that detector exists. |

## General principles applied throughout

- Every event's `possible_interpretation` is hedged ("possible",
  "consistent with", "candidate") -- see docs/event-schema.md.
- `requires_human_review` defaults to `True` everywhere.
- When a detector cannot corroborate its primary signal (e.g. no audio
  track to check against a freeze), it says so explicitly in
  `observations`/`limitations` rather than assuming the worst or the best
  case.
- No detector in this codebase suppresses a finding entirely based on a
  heuristic guess that it's probably fine -- it downgrades severity/
  confidence instead, so the operator still sees it (at low priority) but
  is not told it's confirmed.
